2. WHY WE USED THESE SPECIFIC TECHNOLOGIES (PLAIN-ENGLISH DEFENSE) Architecture Rationale
WHY CITUS? Horizontal Distributed Sharding
Problem: Standard PostgreSQL chokes on single-node disk I/O, table locking, and memory overhead when managing 60M+ flight records and high-frequency concurrent seat hold transactions.
Why Citus: Transforms PostgreSQL into a distributed database. Data is partitioned across worker nodes using flight_id as shard key. Scaling CPU cores and disk IOPS horizontally without rewriting SQL queries.
WHY CQRS? Port 5433 Search Read Replica
Problem: In airlines, 99.8% of user operations are flight searches; less than 0.2% are bookings. Heavy search queries lock tables and starve critical checkout transactions.
Why CQRS: Complete Command-Query Separation. All search traffic hits a dedicated denormalized Read Replica (Port 5433) in < 40ms. The Write Coordinator (Port 55432) remains 100% dedicated to atomic bookings.
ROW-LEVEL CAS LOCKS Zero Oversell
Uses conditional SQL predicates: available_seats = available_seats - 1 WHERE available_seats >= 1. Relies on Postgres MVCC row locks rather than slow Redis locks.
TRANSACTIONAL OUTBOX Saga Integrity
Seat reservation and outbox event are written inside the same atomic ACID transaction. Even if the server dies mid-flight, events are never lost and sagas auto-reconcile.
REDIS CACHE Sub-2ms Speed
Caches airport metadata, user JWT sessions, and hot flight searches. Relieves database from repeated queries while Citus handles financial-grade inventory balance.
Jury Elevator Pitch: "AeroScale solves the billion-dollar airline problem: how to query 60 Million flights instantly without letting heavy search traffic interfere with the atomic row locks required to guarantee ZERO passenger overselling under extreme holiday booking spikes."

3. HOW IT WORKS UNDER THE HOOD: THE 3 CORE ENGINEERING INVARIANTS Technical Depth
INVARIANT 1 Citus Table Co-Location (Eliminating Distributed 2PC Overhead)
• Both flights and flight_seats tables are distributed with: SELECT create_distributed_table('flight_seats', 'flight_id', colocate_with => 'flights');
• Why this is crucial for the Jury: Co-location guarantees that Shard 102001 of flights and Shard 102001 of flight_seats live on the exact same physical worker node!
• When a user books a flight, the query executes as a single-node local ACID transaction on that worker. It avoids expensive distributed network locks and cross-node Two-Phase Commit (2PC), giving enterprise throughput (> 2,500 bookings/sec).
INVARIANT 2 Mathematical Anti-Oversell Conditional Decrement (Compare-And-Swap)
• Instead of a naive SELECT available_seats followed by application-level UPDATE (which creates race conditions), AeroScale uses atomic database-level predicate locking:
UPDATE flight_seats SET available_seats = available_seats - 1 WHERE flight_id = $1 AND cabin_class = $2 AND available_seats >= 1 RETURNING available_seats;
• Concurrency Invariant: PostgreSQL MVCC serializes row updates on the unique (flight_id, cabin_class) tuple. If counter is 0, the WHERE clause evaluates to false; rowCount = 0. The transaction rolls back immediately and returns 409 Conflict. It is mathematically impossible to oversell even with 1,000 racing threads.
INVARIANT 3 The 300-Second Hold & Two-Phase Saga Auto-Reconciliation
• When a passenger selects a seat, inventory is decremented and marked status = 'HELD' with expires_at = NOW() + INTERVAL '5 minutes'.
• An event is atomically recorded in outbox_events. A background Saga Reconciler polls for uncommitted holds. If the passenger abandons payment or the browser disconnects after 300s, the Saga triggers a compensating transaction: restoring available_seats = available_seats + 1, marking booking 'EXPIRED', and returning the seat to the open market.

5. ADVANCED VIVA QUESTIONS & HIGH-SCORING DEFENSE ANSWERS Examiner Q&A
Q1 Why Citus sharding instead of standard Postgres primary-replica setup?
Answer: Standard read replicas only scale read operations; all writes still hit one single master disk and CPU, creating an absolute bottleneck. Citus shards both tables and indexes across worker nodes, providing horizontal scaling for both reads and concurrent writes while allowing a 60M dataset to exceed single-machine RAM limits.
Q2 How does AeroScale adhere to the CAP Theorem?
Answer: We make a deliberate split based on business domain: For Seat Inventory & Bookings, we choose CP (Consistency & Partition Tolerance) — if network partitions occur, we fail fast rather than risk overselling. For Flight Browsing/Search, we choose AP (Availability & Partition Tolerance) via the CQRS replica where eventual consistency (lag < 50ms) is completely acceptable.
Q3 What prevents distributed deadlocks during simultaneous multi-seat bookings?
Answer: Two mechanisms: First, shard co-location ensures all seat counters for a given flight live on the exact same worker, meaning locks are resolved by Postgres’s local deadlock detector. Second, our application enforces a deterministic lock acquisition order (sorting seat IDs in ascending order before executing updates), mathematically preventing circular lock wait chains.
Q4 What transaction isolation level is used and why not Serializable?
Answer: We use Read Committed with Atomic Conditional Updates. SERIALIZABLE isolation aborts high numbers of transactions with serialization failure errors (40001) under heavy concurrency, requiring complex retry loops. Our atomic conditional decrement achieves 100% mathematical safety directly at the storage engine level with zero retry penalty.
Q5 What happens if the server crashes right after taking the passenger's money?
Answer: The Transactional Outbox pattern guarantees safety: the booking record and outbox event are committed atomically in the same database transaction. The background Saga worker replays unhandled events with idempotent keys, ensuring notifications, ticket emission, and payment capture complete reliably with zero orphan bookings.
Q6 Why not store inventory counters in Redis using DECR instead of Citus?
Answer: Redis DECR is in-memory and fast, but Redis is not fully ACID. During an unexpected power loss or failover, asynchronous replication (RDB/AOF) can lose state, resulting in catastrophic overselling. In AeroScale, Citus acts as the single source of truth for financial-grade inventory, while Redis is used strictly for read caching.
Q7 What caused the Citus maintenance daemon error and how was it solved?
Answer: The maintenance daemon on worker2 was failing to connect to worker1:5432 with fe_sendauth: no password supplied. Citus workers require bidirectional internal communication for maintenance tasks. We resolved this by creating trust rules on the internal Docker network, allowing workers to authenticate transparently without exposing ports externally.
