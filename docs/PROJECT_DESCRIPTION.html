01

A correctness problem at airline scale

Airline inventory looks like a CRUD application until two customers buy the last seat at the same moment. Then it becomes a distributed-systems problem: the same fact is being changed from several processes, on several machines, and the business loses money when the copies disagree.

The system sells seats on scheduled flights. Each flight has cabins, each cabin has a capacity, and a booking moves through a hold and a payment before it becomes a sale. Four invariants must hold no matter how many API instances are running or how many buyers race for the same row:

  1. Capacity. A cabin never sells or holds more seats than it has.
  2. Seat identity. At most one live booking may hold a given physical seat on a given flight.
  3. Exactly-once effect. A retried request, a duplicated message, or a replayed event must not create a second booking or consume a second seat.
  4. Read availability. Search must stay fast while the write model changes continuously.

The scale makes the obvious designs fail:

Naive designWhy it breaks
One row per physical seatAt 50 million flights with roughly 200 seats each, this is about 10 billion rows before a single booking exists. The seat table, its indexes and every seat-map query become the bottleneck.
Counter read, then write, in application codeTwo buyers read available = 1, both subtract one, both write 0, and two seats are sold. The lost update is invisible until the flight departs.
Shard by booking identifierThe booking, its payment and the inventory counter it changes can land on different shards, so one logical operation needs a distributed commit.
One large PostgreSQL serverCorrect, but write throughput, storage and read traffic all have to fit on one machine. The interesting question is what to do when they do not.
Design thesis

Choose a distribution key that makes the invariant local. Enforce the invariant in one SQL statement whose predicate the database re-checks while holding the row lock. Move everything that cannot be local into an explicitly eventual, rebuildable projection fed by a transactional outbox.

Every decision in the rest of this document follows from that thesis. The distribution key is flight_id. The anti-oversell rule is a conditional UPDATE. Search and the per-user booking list are projections, not authoritative tables.

02

Runtime architecture

The deployment is a shared-nothing write cluster with a separate read store and a stateless application tier. The API never chooses a shard; it issues ordinary SQL to the Citus coordinator, which plans the query, routes each fragment to the worker that owns the relevant shard, and merges the result.

Figure 1. Runtime topology. Solid lines are synchronous request paths; dashed lines are background or bulk paths. The coordinator owns no business rows: it holds shard metadata and query planning. Reference tables are replicated to both workers, so dimension joins stay local.

Components and responsibilities

ComponentResponsibility
API tierExpress application, fully stateless. Any instance can serve any request. NODE_ID is written into logs, the x-node-id response header and bookings.node_id. Scale by adding replicas.
PgBouncerTransaction pooling in front of the coordinator. Safe because the booking path keeps no session state between statements and uses no named prepared statements.
Citus coordinatorQuery planning, shard routing and result merging. It stores no business rows. This is the single logical endpoint for writes.
worker1 / worker2Physical shard storage and replicated reference tables. The placement of each shard is recorded in pg_dist_placement.
Read model databaseAn independent PostgreSQL 17 database holding flight_availability and projection_state. Deliberately outside the Citus cluster: search may lag, and a slow search must not hold a lock that blocks a sale.
RedisIdempotency claims (SET NX), rate limits and caches. Optional: without it the process-local driver keeps single-node correctness, and the database constraints remain the real guarantee.
Background workersOutbox projector, hold reaper and saga reconciler. Kept in a separate process from the API so a worker crash never takes the API down.

The same application code runs against a single local PostgreSQL instance and against a Citus cluster. Migrations detect the capability and either distribute tables or leave them as ordinary local tables. That portability is what lets the test suite run without Docker while the deployment runs distributed.

Why the keys look unusual

Every primary key contains both the distribution column and the partition key. Citus requires the distribution column in every unique constraint; PostgreSQL requires every partition-key column in the primary key of a partitioned table. The composite keys are a consequence of those two rules, not an arbitrary modelling choice.

3.6 Partitioning on top of distribution

Every large write-model table and the read-model availability table is also range-partitioned by month on departure_date. Distribution and partitioning solve different problems and the design uses both:

Hash distribution

Decides which worker owns a row. Hash of flight_id or user_id, 32 shards by default, placed across the workers.

Range partitioning

Decides which physical table owns a row. One partition per calendar month of departure_date. Old months are dropped as partitions, not deleted row by row.

Two SQL helpers in migration 001 do the maintenance work: app_ensure_month_partitions(parent, months_behind, months_ahead) creates the missing monthly partitions, and app_drop_partitions_older_than(parent, months) removes expired ones. Migration 007 creates the initial window; src/db/partitions.js plans the window, detects gaps, creates missing partitions, drops old ones behind a row-count guard and a dry-run option, and serialises the whole operation under an advisory lock so two maintenance jobs cannot race.

Partition pruning is only useful if queries carry the partition key. This design makes that true by construction: a booking always knows its departure_date, findById takes both key parts, the inventory update names both, and the outbox publisher marks an event by (flight_id, departure_date, event_id). A query that omits the date can still run, but it scans every partition; the code avoids that on every hot path.

Consequence worth stating in a presentation

Citus gives each partition its own set of shards. A table with 32 hash shards and 26 monthly partitions has 832 shard placements for that table alone. This is normal for distributed PostgreSQL, but it is why shard counts and partition horizons are capacity decisions, not free knobs.

3.7 Time-ordered identifiers

Primary keys default to UUIDv7, either the native uuidv7() where the server provides it or a PL/pgSQL fallback that builds a 48-bit millisecond timestamp, a version nibble and an RFC 4122 variant. Time-ordered keys insert at the right edge of the B-tree instead of scattering across it the way random v4 keys do. At tens of millions of rows that is the difference between a healthy index and constant page splits. The same generator is used for booking, payment and event identifiers.

3.8 Logical relationships

The schema uses no foreign keys between distributed tables. Relationships are logical, enforced by the write path and checked by the audit. This avoids cross-shard foreign-key checks and keeps every write local.

04

How this demonstrates a distributed database

Citus keeps the PostgreSQL interface and adds a coordinator, shard placement and distributed query planning underneath it. The application still writes SQL; the difference is that each statement may be routed to one worker or fanned out to many. This project uses five mechanisms deliberately, and each one is visible in the schema and the code.

4.1 Horizontal fragmentation by flight_id

flights is distributed on flight_id with 32 hash shards. Every row belongs to exactly one shard; every shard belongs to one worker. The mapping is not in application code. It lives in the Citus catalogs: pg_dist_node for workers, pg_dist_partition for the distribution column, pg_dist_shard for shard ranges and pg_dist_placement for shard-to-node placement.

-- db/migrations/003-flights-and-inventory.js
SELECT create_distributed_table('flights', 'flight_id', shard_count => 32);

-- Same distribution column, same shard count: the same colocation group.
SELECT create_distributed_table('bookings', 'flight_id', colocate_with => 'flights');

src/db/citus.js reads those catalogs to produce a topology report: coordinator, workers, shard count, distribution column and co-location groups. The health endpoint exposes the capability block, and the admin topology endpoint exposes the fuller report. This is how the running system can answer "which of these am I talking to?" without opening a psql session.

4.2 Co-location makes the booking transaction local

This is the central design decision. flights, flight_inventory, bookings, payments and booking_outbox all distribute on flight_id and all specify colocate_with => 'flights'. The same flight_id therefore hashes to the same shard, and every table in the group puts that shard on the same worker.

A booking creates five writes in one transaction:

  1. Statement 1 · flight_inventoryDecrement the counter and increment the hold. One row, one shard.
  2. Statement 2 · bookingsInsert the PENDING booking. Co-located with the counter, so the same shard.
  3. Statement 3 · paymentsInsert the PENDING payment with saga state RESERVED. Same shard.
  4. Statement 4 · booking_outboxInsert BOOKING_RESERVED. Same shard.
  5. Statement 5 · booking_outboxInsert INVENTORY_CHANGED with the new counter snapshot. Same shard.

Because all five rows share the distribution key, the coordinator sends one transaction to one worker. That worker runs an ordinary local PostgreSQL transaction. If any statement fails, the rollback is local and complete: no seat is held, no booking exists, no event exists. There is no two-phase commit, no distributed deadlock across workers and no window in which half the writes are visible.

The trade-off, stated plainly

Co-location is what removes the distributed commit, and it also constrains the schema. Every unique constraint has to contain flight_id, and a transaction cannot touch two flights. The system is designed so that it never needs to: one booking is one flight.

4.3 Reference tables keep dimension joins local

Dimensions are small, read-mostly and joined by almost every query. Replicating them in full is cheaper than shipping rows between workers. Migration 008 promotes airlines, airports, cabins, aircraft_types, seat_map_templates and users to Citus reference tables.

The consequence is that a query such as "find this flight, then look up its cabin price and airport names" can join the distributed fact row to the reference rows on the same worker. The coordinator does not need to gather dimension rows from another node. The price of this choice is that every write to a reference table is replicated to every worker, which is why the set is limited to small, slowly changing data.

4.4 A second distribution key, on purpose

Bookings are distributed by flight_id because that is what keeps a booking transaction local. But the question "show me my bookings" is asked by user_id, and answering it against bookings would fan out to every flight shard. No single distribution key serves both access paths well.

The design resolves this with a second table, user_bookings, distributed by user_id and co-located with refresh_tokens. It is a projection, not a second source of truth. The write path never touches it. The outbox projector maintains it, and a guarded upsert makes replay safe. The same split appears in refresh_tokens: token rotation is a per-user transaction that needs no 2PC because the rows are co-located by user_id.

What this demonstrates

In a distributed database, the physical key is chosen per access path, not per entity. The same business object can have an authoritative row in one distribution group and a denormalised index in another, as long as the system states which one is authoritative and how the copy is repaired.

4.5 Two-dimensional placement: hash and range

The tables are distributed and partitioned. Hash placement answers "which worker"; range partitioning answers "which physical table". A query for one flight on one date is routed to one shard and prunes to one monthly partition. A query for a route across a month touches one partition per shard, which is still bounded.

Partitioning also gives the system a cheap retention policy: dropping a departed month is a metadata operation, not a delete of millions of rows. The maintenance job keeps six months ahead of today, one month behind, and retains 24 months by default. It refuses to drop a partition that still contains rows unless explicitly allowed, which prevents a misconfigured retention window from erasing live data.

4.6 Single-shard routing versus scatter-gather

Not every query can carry the distribution key. The design is explicit about which is which.

4.7 Distributed-schema rules the design had to obey

  • Unique constraints must include the distribution column. This explains the composite primary keys, the per-flight booking-reference index and the per-flight idempotency index. A globally unique index would require a coordinator-level check or a different distribution strategy.
  • Foreign keys are not used between distributed tables. Relationships are logical and enforced by the write path. regions is deliberately a plain lookup with no foreign key from distributed tables, as migration 012 documents.
  • Citus rejects DDL inside a distributed transaction. Migrations that distribute or alter distributed tables declare transactional: false, and every statement is individually idempotent so a partial run can be re-run safely.
  • Nullable columns can be added without a rewrite. Migration 012 adds region to five tables as a nullable column with no default, so it is a metadata-only change even on large tables.
  • Dates must not shift. The pool parses PostgreSQL DATE as a string. The default parser builds a local-midnight JavaScript date, which can render as the previous day in UTC. Since departure_date is a partition key and part of every primary key, a one-day shift is a lookup that misses the row it just wrote.

4.8 Topology convergence and worker failure

scripts/citus-init.js converges a cluster to the intended topology rather than assuming it. It can add a worker, verify the existing placement or run a dry run, and it checks the properties the rest of the design depends on:

  • the five booking tables use flight_id, have one co-location group and are actually distributed;
  • user_bookings uses user_id;
  • the flight group and the user group are distinct co-location groups;
  • the six reference tables are reference tables;
  • every worker is reachable.

The script exits 0 for converged, 1 for a failed check and 2 for a usage error, which makes it usable as a deployment gate. The integration test tests/integration/topology.test.js asserts the same properties from the test suite, including the opt-in CITUS_CHAOS=1 case that disables a worker and checks that the cluster remains available for the shards it still holds.

05

Concurrency control and the invariants

The distributed design decides where the data lives. The concurrency design decides what happens when two requests arrive at the same row at the same time. In this system that is one SQL statement, backed by constraints and an audit.

5.1 The anti-oversell statement

UPDATE flight_inventory
   SET available_seats = available_seats - $5,
       held_seats      = held_seats + $5,
       version         = version + 1,
       updated_at      = now()
 WHERE flight_id      = $1
   AND departure_date = $2
   AND cabin          = $3
   AND shard_no       = $4
   AND available_seats >= $5
   AND ($6::bigint IS NULL OR version = $6)
RETURNING flight_id, departure_date, cabin, shard_no,
          total_seats, available_seats, held_seats, version, updated_at;

PostgreSQL takes a row lock for the update. A concurrent writer waits, and when it acquires the lock the predicate is re-evaluated against the committed row. If the first buyer took the last seat, the second buyer's available_seats >= 1 is now false, the statement updates zero rows, and the service returns SOLD_OUT. There is no read-then-write window in which a lost update can hide, which is why the code does not use SELECT ... FOR UPDATE followed by an UPDATE: two statements would add a round trip and an interval the database does not need.

A zero-row result is an expected business outcome, not an exception. The repository then performs an advisory read to distinguish three causes: no inventory row, sold out, or an optimistic version conflict. That read never decides whether the sale happened; the UPDATE already did.

5.2 The accounting model

Each cabin counter has three visible quantities: total_seats, available_seats and held_seats. Confirmed seats are derived, not stored: total − available − held. Every transition is a guarded statement.

TransitionCounter movementGuard
Reserveavailable − n, held + navailable >= n, optional version = expected
Confirmheld − n; confirmed grows by nheld >= n
Releaseheld − n, available + nheld >= n
Reclaimavailable + n; confirmed shrinks by navailable + held + n <= total

Two equalities are audited, not one inequality:

-- For every (flight, date, cabin):
held_seats                 = number of live PENDING bookings
total_seats - available_seats - held_seats
                           = number of CONFIRMED bookings

The database CHECK (available_seats + held_seats <= total_seats) prevents an over-capacity counter. It cannot detect drift between the counter and the bookings table, because each table is internally consistent while the two disagree. inventoryRepository.audit runs the two equalities in one local query and reports four violation types: NEGATIVE_COUNTER, OVERCAPACITY, HELD_MISMATCH and CONFIRMED_MISMATCH, each with the signed size of the difference.

5.3 One live booking per physical seat

Capacity and seat identity are separate resources. The counter protects the cabin; a partial unique index protects the seat:

CREATE UNIQUE INDEX uq_live_seat
    ON bookings (flight_id, departure_date, seat_number)
 WHERE seat_number IS NOT NULL
   AND status IN ('PENDING', 'CONFIRMED');

The predicate is what makes the index a live seat index. Cancelled and expired rows leave the predicate and stop blocking the seat, without deleting history. A losing insert raises SQLSTATE 23505; the service translates the constraint name into SEAT_UNAVAILABLE, never a 500. Because the reservation and the failed insert are in one transaction, the loser's rollback returns its seat to the counter.

5.4 Idempotency at two layers

A retry is not an edge case in a distributed system; it is the normal response to an ambiguous timeout. The system uses two layers with different failure modes:

Redis claim and record

SET NX claims the key. The request hash is stored with the claim. A replay with the same body returns the stored response; a different body is a conflict; an in-flight duplicate waits briefly and then receives a 409 with a retry hint.

Database partial unique index

uq_booking_idempotency on (flight_id, departure_date, idempotency_key). If two requests race past the cache, one insert wins and the other is translated into a replay or a duplicate-booking error.

The cache is allowed to fail. Without Redis, the in-process driver still deduplicates within one API instance, and the database index still prevents two bookings for one key on the same flight. Correctness never depends on the cache being available, which is why the health endpoint reports the in-memory driver as a supported fallback rather than a failure.

Failure outcomes are durable too. A declined payment writes an error record against the idempotency key, so a retry sees the same decline instead of authorizing the card a second time. A rolled-back transaction releases the claim, so a retry can genuinely try again.

5.5 Retrying the whole transaction

Transient SQLSTATEs are retried around the entire transaction, never around the last statement. Replaying only the failed statement would re-run a reservation whose earlier attempt may already have committed, which is exactly how a counter drifts. The retry policy separates:

  • Retryable: serialization failure (40001), deadlock detected (40P01), connection loss and selected Citus node errors.
  • Never retryable: unique and check violations, validation errors, not found, and application conflicts. Retrying these would repeat a decision the database has already made.

Backoff is exponential with full jitter: four attempts by default, 15 ms initial delay, 200 ms ceiling. Full jitter matters when many clients retry the same hot flight; without it they resynchronise and hit the row in a thundering herd.

5.6 Claim-based state transitions

Status transitions are conditional updates that claim the row, not read-then-write sequences:

UPDATE bookings
   SET status = 'CONFIRMED', confirmed_at = now(), updated_at = now()
 WHERE flight_id = $1 AND departure_date = $2 AND booking_id = $3
   AND status = 'PENDING'
RETURNING ...;

The same pattern covers cancel and expire. claimForCancel accepts PENDING or CONFIRMED and returns (confirmed_at IS NOT NULL) AS was_confirmed, which tells the caller whether to release a hold or reclaim a sale. claimForExpire accepts only a PENDING booking whose hold_expires_at has passed.

This is how the confirm-versus-reaper race resolves. If the reaper expires the hold first, the confirm claim updates zero rows and the saga compensates. If the confirm wins, the reaper's claim updates zero rows and it leaves the booking alone. No lock is held across the payment call, and no process has to trust that the other one is not running.

06

The booking saga

A database transaction cannot be held open across a payment gateway. The system therefore splits the booking into a short local transaction, an external payment sequence and a second local transaction, and persists enough state that any step can be resumed or compensated.

6.1 The sequence

  1. Transaction A · reserveHold the seat and write the intent. Reserve inventory, insert the booking as PENDING, insert the payment as PENDING / RESERVED, and write BOOKING_RESERVED plus INVENTORY_CHANGED to the outbox. All five rows are one local transaction on one worker.
  2. Outside any transaction · authorizeCall the payment gateway. Mark the payment AUTHORIZING, call the provider, mark it AUTHORIZED or failed. Holding no database transaction across a network call is deliberate: a slow gateway must not hold a row lock.
  3. Outside any transaction · captureCapture the authorized amount. Mark CAPTURING, capture, mark CAPTURED. If the hold expired while the gateway was working, the code refunds and compensates rather than confirming a seat it no longer owns.
  4. Transaction B · confirmConvert the hold into a sale. Claim the booking PENDING → CONFIRMED, consume the held seat, mark the payment CONFIRMED, and write BOOKING_CONFIRMED plus INVENTORY_CHANGED.
  5. Compensation · on failureUndo in reverse order. Refund or void outside the transaction, then claim the booking cancelled, release or reclaim the exact inventory row, mark the payment, and write BOOKING_CANCELLED plus INVENTORY_CHANGED.

The persisted payments.saga_state is what makes the sequence recoverable. A crash after authorization leaves AUTHORIZED on disk; the reconciler can continue from there. A crash after capture leaves CAPTURED with a PENDING booking; the forward-recovery branch detects that combination and completes the confirmation instead of refunding a successful sale.

6.2 Inline and asynchronous execution

With BOOKING_SAGA_INLINE=true (the default), the request runs the whole saga and answers 201 with a confirmed booking. With it false, the request returns 202 after transaction A, and the saga reconciler drives the remaining steps. Both modes use the same advanceSaga function, which re-reads persisted state on every call and claims each transition conditionally. That is what makes the same code safe as the request path and as the recovery path.

The reconciler scans stale PENDING bookings and stuck payments. Compensation counts as a successful outcome, because the goal is a terminal, consistent state, not a confirmed sale at any cost.

6.3 Hold expiry

A hold that is never paid must not consume a seat forever. BOOKING_HOLD_TTL_SECONDS defaults to 600 seconds. The reaper scans open holds in batches, claims each one PENDING → EXPIRED, and only then releases the exact counter row recorded on the booking. It skips any payment that is already CAPTURED, because refunding a captured payment is the saga's job, not the reaper's.

The ordering matters. Claim first, release second. If the processes were reversed, a crash between the two would return a seat for a booking that is still live, and a later confirmation would consume a seat twice. Claiming first makes the state transition the decision point, and the release is safe to retry because held_seats >= count makes a double release a no-op.

6.4 Cancellation

Cancellation is not one operation. If the booking was PENDING, its seat is held, so the correct action is release. If it was CONFIRMED, its seat has already left held_seats, so releasing would find nothing and silently leave the seat unsold. The cancel claim returns was_confirmed from confirmed_at, and the service chooses reclaim or release accordingly. A captured payment is refunded; an authorized one is voided; a pending one is simply failed.

Why the saga belongs in a distributed-systems course

It is the standard alternative to a distributed transaction when one participant is external and cannot enlist. The project shows the two properties a saga needs to be trustworthy: every step is idempotent or conditionally claimed, and every intermediate state is persisted so recovery does not depend on the process that started the work.

07

Consistency across stores

The write model, the per-user index and the search database cannot be updated atomically without a distributed transaction across independent databases. The system accepts that, and replaces atomicity with a protocol that is recoverable, replay-safe and measurable.

7.1 The dual-write problem

Writing the booking and then writing the read model in the request path is fast until the process dies between the two. After that, the stores disagree and nothing records the gap. The system avoids dual writes entirely: the event is written to the outbox inside the same transaction as the state change, and a separate poller projects it. If the process dies after commit, the event is durable and will be projected. If it dies before commit, nothing happened at all.

7.2 The outbox protocol

-- Delivered by src/workers/outboxConsumer.js, one event per transaction.
BEGIN;
  -- 1. project into user_bookings and/or flight_availability
  -- 2. only after that write commits:
  UPDATE booking_outbox
     SET published = true, published_at = now()
   WHERE flight_id = $1 AND departure_date = $2 AND event_id = $3;
COMMIT;

The ordering is project first, mark published second. A crash between the two replays the event, which is safe because every projection write is a guarded upsert. The opposite order would turn a crash into a permanently lost projection, silently. Between "may apply twice" and "may lose one", at-least-once with idempotent writes is the only recoverable choice.

Each event is projected in its own transaction, so one poison event cannot roll back the healthy events behind it. A failed event stays unpublished, its attempt count rises, and the poller applies an exponential cooldown. After the configured maximum it remains parked and visible rather than disappearing.

7.3 Guarded upserts

The read model stores the write-model counter version; the per-user projection stores the event time. Both writes refuse to move backwards:

INSERT INTO flight_availability (...)
VALUES (...)
ON CONFLICT (origin, destination, departure_date, flight_id, cabin)
DO UPDATE SET
  available_seats = EXCLUDED.available_seats,
  held_seats      = EXCLUDED.held_seats,
  source_version  = EXCLUDED.source_version,
  updated_at      = now()
WHERE flight_availability.source_version <= EXCLUDED.source_version;

user_bookings uses the same shape with last_event_at <= EXCLUDED.last_event_at. The comparison is <=, not <, so an identical replay is a no-op rather than an error. A late batch delivered out of order changes nothing.

7.4 Lag is measured and surfaced

The projector updates projection_state.last_event_at with a GREATEST guard, so a replayed old event cannot rewind the watermark. Search responses carry x-read-model-lag-ms, the API returns a freshness block with lagSeconds, and READMODEL_LAG_SLA_SECONDS (60 seconds by default) defines when the projection is considered stale. Prometheus exposes airline_outbox_pending_events, airline_outbox_lag_seconds and airline_read_model_lag_seconds.

Surfacing lag is a design position, not a diagnostic afterthought. A read model that is allowed to lag must tell its readers how far behind it is, or the first stale search result becomes a correctness argument.

7.5 The consistency contract

7.6 Rebuilding what can lag

Because the read model is derived, it can be repaired. projectionService.reprojectAvailability replays outbox history, optionally for specific flights, and optionally deletes the affected rows first so a rebuild can remove a row that should no longer exist. reprojectUser rebuilds one user's index directly from the authoritative booking table. The operational scripts expose both behind npm run readmodel:reproject. This is the practical meaning of "derived": if it is wrong, replay history rather than patch it.

08

End-to-end request paths

8.1 Creating a booking

  1. HTTPValidate the request and resolve the flight. The API normalises cabin and seat, checks the flight is not cancelled or departed, and loads cabin metadata. These reads happen outside the write transaction to keep it short.
  2. IdempotencyClaim the key if one was supplied. A replay returns the stored response with status 200; an identical request still in flight returns 409 with a retry hint; a different body under the same key is a conflict.
  3. Transaction AReserve, insert booking, insert payment, write two outbox events. One checked-out client, one worker, one local transaction, retried as a whole on transient failure.
  4. PaymentAuthorize and capture outside the transaction. Failure injects a durable declined outcome and starts compensation.
  5. Transaction BConfirm the booking and consume the hold. Claim PENDING → CONFIRMED, decrement held_seats, mark the payment captured, write the confirmation events.
  6. Response201 with the booking, or 202 when the saga is deferred. The response carries the node id, and the idempotency record is completed with the result.
  7. AsynchronouslyThe projector drains the outbox. Search and user_bookings catch up; lag is visible until they do.

8.2 Searching for flights

Search reads flight_availability from the read database, or from READMODEL_READ_URL when a replica is configured. One SQL statement uses three CTEs: matched applies the route, date and filter predicates; page applies ordering and pagination; total returns the count. A LEFT JOIN LATERAL aggregates the cabin rows into a JSON array, so one flight returns one result object with all its cabins rather than one row per cabin. The response carries freshness metadata derived from the projection watermark.

The query is indexed by (origin, destination, departure_date, available_seats). It does not touch the Citus write cluster at all, which is the point: search traffic cannot contend with booking traffic.

8.3 The seat map

Seats are derived, never materialised per flight. The aircraft type selects a template from seat_map_templates; the live seat numbers for that flight are read from bookings where the status is PENDING or CONFIRMED; the two are left-joined and returned by cabin. A 180-seat aircraft returns 180 rows for that flight regardless of how many flights exist in the system. The template also supplies window, middle, aisle and exit-row metadata, so the seat map is a rendering concern rather than a storage one.

8.4 Health and readiness

Three probes answer three different questions. Liveness never touches a dependency, so a database outage cannot make an orchestrator kill a healthy process. Readiness checks both models and fails with 503 while either is unreachable, which removes the instance from the load balancer. Health is the full report: reachability, latency, Redis driver, Citus capability and topology. The read model being down produces DEGRADED, not DOWN, because booking still works; calling that state DOWN would take a node out of service for a dependency it does not need in order to sell a seat.

09

Operations at scale

9.1 Migrations

Migrations are plain JavaScript modules that receive a checked-out client, so they can branch on whether Citus is present. Each target database keeps its own schema_migrations table with a SHA-256 checksum of the migration source. Editing an applied migration is reported as drift instead of being silently ignored. Transactional migrations roll back completely on failure; non-transactional ones are written to be idempotent, which is what makes a partially applied Citus DDL step safe to re-run.

9.2 Partition maintenance

npm run partitions:maintain creates upcoming monthly partitions and drops months past retention. It runs under an advisory lock, supports a dry run, refuses to drop a partition containing rows unless explicitly allowed, and can detach instead of drop. The operation is idempotent and reports the plan before acting.

The health and admin endpoints expose the Citus topology, so a dashboard can show the same shard and co-location facts the planner uses.

9.4 Bulk loading

The Python loaders implement the volume path: users, flights with inventory, then the read model. They use COPY, write in day order so writes stay inside one monthly partition at a time, and checkpoint after each fully committed day. Flight identifiers are deterministic UUIDv5 values derived from region, date and sequence, so a re-run reproduces the same rows and upserts are idempotent. The design target is 50 million flights and 100,000 users across five regions and two years of schedules.

On the machine used for this deployment the full target did not fit on disk, so the measured run loaded 10,000,017 flights, 22,064,378 inventory rows, 100,004 users and 22,064,378 read-model rows, about 13 GB in total. The numbers in the evidence section are from that run.

9.5 Load and chaos testing

k6 scenarios separate the read path from the write path. The booking scenario treats a 409 as the anti-oversell condition doing its job, not as a failed request. scripts/chaos-worker-down.js stops the background workers, keeps accepting bookings, restarts the workers and verifies that the read model catches up with a clean inventory audit. That is the operational claim the outbox exists for: the API keeps selling while projection is down, and recovery is automatic.

9.6 Deployment

Docker Compose runs a coordinator, two workers, the read model, Redis, PgBouncer, the API, an optional migration job and optional workers, with Prometheus under an observability profile. Kubernetes manifests, probes, scaling notes and the migration-before-rollout order live in deploy/k8s/. The same image runs the API, the workers and the migration job.

A course presentation is stronger when it states what the design gives up. These are deliberate choices, not omissions discovered later.

Two larger limitations are worth naming. The coordinator is a single logical entry point in the Compose deployment; production high availability for it is an infrastructure concern that the code does not solve. And the system is single-tenant: there is no row-level security or per-tenant isolation. Both are reasonable scope choices for a course project, and both should be said out loud rather than left for a reviewer to find.

Partition maintenance is external. The application exposes the tooling and the advisory lock, but something has to schedule it. The same is true of the reaper and the projector: they run in-process by default, and a production deployment should run them as separate workers so a restart of the API does not pause projection.

Three questions a reviewer is likely to ask

Why not one shard per flight?

A hash of flight_id into 32 shards spreads millions of flights across workers while keeping every flight's rows together. One shard per flight would create millions of tiny shards and an unmanageable catalog.

Why not use 2PC for the read model?

The read model is a separate database and is allowed to lag. A two-phase commit across two databases would make search part of the booking critical path, which is exactly what the CQRS split avoids. The outbox gives at-least-once delivery with idempotent writes instead.

What happens if a worker dies mid-booking?

The transaction was local to that worker. If it had not committed, the client's retry is safe because the whole transaction is replayed; if it had committed, the booking and its outbox event are both durable, and the projector or reconciler continues from persisted state. No other shard is involved, so there is nothing to coordinate.

A suggested order for a course presentation. Each step produces something visible, and the sequence builds from "it works" to "here is why it is distributed".

  1. 1 · StartBring up the local stack. Run the migration and show npm run db:status reporting applied migrations and, on the Citus path, the coordinator, workers and shard distribution.
  2. 2 · SchemaShow the placement map. Open §3.2. Point out the five tables in one co-location group and the separate user group. This is the single most important slide.
  3. 3 · TopologyQuery the catalogs. Run the topology endpoint or scripts/citus-init.js --verify. Show pg_dist_partition and pg_dist_placement proving the distribution column and shard placement.
  4. 4 · BookCreate a booking with an Idempotency-Key. Show 201, the booking row, the payment row and the outbox rows. Send the same request again and show 200 with the same booking.
  5. 5 · OversellRun the concurrency test. Show 25 requests against capacity 5, five confirmed, twenty SOLD_OUT, and a clean audit.
  6. 6 · SeatRun the seat race test. Show ten buyers for one seat and exactly one winner.
  7. 7 · Read modelSearch before and after the projector drains. Show the read-model row, the freshness watermark and the lag header. Then replay an older event and show the projection does not move backwards.
  8. 8 · FailureRun the worker-down chaos test. Stop the workers, keep booking, restart them, and show the read model catching up with a clean audit.
  9. 9 · ScaleShow the measured load table. Ten million flights, twenty-two million inventory rows, one hundred thousand users. Explain what the counter model avoided.
  10. 10 · CloseReturn to the thesis. Local key, local invariant, explicit eventual copies. Then open the concept map and invite questions against it.
The one sentence to leave in the room

The database enforces the invariants, the distribution key makes those invariants local, and everything that cannot be local is an explicitly eventual projection with a measurable lag and a rebuild path.
