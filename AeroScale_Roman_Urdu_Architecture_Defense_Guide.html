1. AIRLINE INVENTORY KA ASAL CHALLENGE KYA HOTA HAI? Core Problem
CHALLENGE 1 Search vs. Booking Ka Tazaad (99.8% vs 0.2%)
Airline websites pe 99.8% log sirf ticket price aur timing search karte hain, sirf 0.2% log waqayi ticket khareedte hain. Agar aik hi database pe dono traffic chala dein to hazaaron search queries database ke tables lock kar dengi, jis se booking transactions fail ho jayengi.
CHALLENGE 2 Race Condition & Overselling Disaster
Eid ya Christmas sale par jab flight ki aakhri seat bachti hai, to 500 log aik hi second mein "Pay Now" dabate hain. Agar traditional system ho to pehle check karega available_seats > 0, dono ko true milega, aur dono ko ticket issue ho jayegi (Oversell disaster).
CHALLENGE 3 60 Million Records Ka Scale
Aik normal database 5 se 10 million rows ke baad slow ho jata hai kyunke indexes itne baray ho jate hain ke RAM se bahar nikal kar disk pe swapping shuru ho jati hai. 60M records ko real-time handle karne ke liye database sharding lazmi hoti hai.
CHALLENGE 4 Ghost Holds & Partial Failures
Agar user seat cart mein daal kar tab close karde, ya payment gateway fail ho jaye, to seat permanently block na ho. Iske liye automated self-healing saga reconciliation zaroori hota hai jo 300 second baad seat wapis release kare.

3
Stage 3: Seat Hold Request & Atomic Row Lock (The Crucial Checkout Step)
User cabin aur seat select karke "Proceed to Reserve" dabata hai. Yeh request Citus Coordinator (Port 55432) pe jati hai. Backend aik ACID transaction shuru karta hai:
UPDATE flight_seats SET available_seats = available_seats - 1 WHERE flight_id = $1 AND cabin_class = $2 AND available_seats >= 1 RETURNING available_seats;
Postgres is row par exclusive lock lagata hai. Agar available seats 0 hon to query 0 rows update karegi, transaction fauran ROLLBACK ho jayegi aur user ko 409 Conflict message mil jayega. Overselling namumkin ho jati hai!
4
Stage 4: Atomic Outbox Event Commit & 300-Second Hold Timer
Agar update kamyab ho, to usi same transaction ke andar bookings table mein record (status = 'HELD', expiry = NOW() + 5 minutes) aur outbox_events table mein event insert hota hai, aur transaction COMMIT ho jati hai. Seat passenger ke liye reserve ho chuki hai.
5
Stage 5: Payment Processing Ya Expiry Reconciliation (Two-Phase Saga)
Scenario A (Success): User 5 minute ke andar payment complete karta hai -> status 'CONFIRMED' ho jati hai aur ticket generate ho jata hai.
Scenario B (Abandon/Timeout): Agar user browser band karde ya payment fail ho, to background Saga Reconciler Worker 300 second baad expired holds dhoondta hai, aur compensating transaction chala kar available_seats = available_seats + 1 karke seat wapis open market mein bhej deta hai.

5. HUM NE POSTGRESQL + CITUS KYUN CHUNA? (THE CORE REASONS) Why Citus?
CITUS ARCHITECTURE PostgreSQL Ko Distributed Cluster Banane Ka Tareeqa
Citus koi alag database nahi hai, balki PostgreSQL ki official open-source extension hai (by Microsoft). Yeh normal Postgres tables ko distributed tables mein tabdeel kar deta hai. 60 Million records aik single computer par rakhne ke bajaye, Citus unhein 51 pieces (shards) mein divide karke multiple worker machines ke CPU cores aur SSDs par spread kar deta hai. Is se hamari write capacity aur query speed dono 10x multiply ho jati hain.
6. ALTERNATIVES COMPARISON: HUM NE DOOSRI TECHNOLOGIES KYUN REJECT KIEN? Alternative Analysis
REJECTED Standard Single-Node PostgreSQL
Kyun Reject Kiya? Normal Postgres mein jab data 5M-10M se barhta hai to B-tree index size physical RAM se bara ho jata hai. Disk I/O 100% ho jata hai aur system freeze hone lagta hai. Single-node vertically scale karne par expensive hardware chahiye hota hai jis ki limit hoti hai.
REJECTED Standard Postgres Read Replicas
Kyun Reject Kiya? Read replicas sirf Reads ko scale karte hain. Jitni bhi bookings, seat holds, aur outbox writes hongi woh sab ab bhi aik hi master database pe jayengi. Master disk bottleneck khatam nahi hota. Citus Reads aur Writes dono ko sharded workers pe scale karta hai.
REJECTED MongoDB / NoSQL Document DBs
Kyun Reject Kiya? MongoDB horizontal sharding to deta hai lekin high-concurrency cross-document ACID transactions mein bohot slow ho jata hai. Airline seat inventory mein strict mathematical atomicity chahiye hoti hai. Mongo ke loose schema mein phantom overselling ka khatra hota hai.
REJECTED Apache Cassandra / DynamoDB
Kyun Reject Kiya? Cassandra Eventual Consistency model par chalta hai (AP in CAP theorem). Airline inventory mein agar aik node pe seat biki aur doosri node ko 2 second baad pata chala, to beech mein 10 log wohi seat book kar chuke honge! Cassandra financial seat inventory ke liye bekar hai.

8. CQRS PATTERN KYUN USE KIYA? (PORT 5433 SEARCH REPLICA) Why CQRS?
CQRS DEFENSE Command Query Responsibility Segregation
Sawal: Hum ne direct Citus Coordinator pe search query kyun nahi chalayi?
Jawab: Airline traffic ka golden rule hai: "Search queries are heavy and read-intensive; Booking transactions are short and write-intensive." Agar Coordinator par aik user 60M flights ka complex filter lagata hai (origin, destination, date, cabin), to database CPU 80% use ho jayega. Usi waqt agar doosra user payment submit kare to timeout ho jayega.
Is liye hum ne CQRS pattern lagaya: Searches ke liye alag Read Model (Port 5433) banaya jo denormalized table rakhta hai. Search traffic kitna bhi barh jaye, hamari booking engine (Port 55432) hamesha 0% disturbance ke sath tez chalti hai!
9. ROW-LEVEL CAS LOCKS VS ALTERNATIVE LOCKING STRATEGIES Concurrency Mechanics
ALTERNATIVE 1 REJECTED Pessimistic Table Locks / SELECT FOR UPDATE
Kyun Reject Kiya? Agar hum SELECT * FROM flight_seats FOR UPDATE lagate, to jab 500 log aik sath aate hain to poori row lock ho jati hai aur baaqi 499 requests queue mein khari ho kar wait karti hain (Lock Convoy). Response time 200ms se barh kar 12 second ho jata hai aur deadlocks aane lagte hain.
ALTERNATIVE 2 REJECTED Application-Side Distributed Locks (Redlock)
Kyun Reject Kiya? Redis Redlock mein lock application level pe lagta hai. Agar network glitch aye ya Node.js garbage collection pause ho jaye, to lock expire ho jata hai jabke transaction abhi chal rahi hoti hai. Nateeja: Do processes aik sath seat book kar leti hain.
AEROSCALE KA SOLUTION Atomic Conditional Compare-And-Swap (CAS)
Hamara code SQL level par conditional predicate use karta hai: WHERE available_seats >= 1. PostgreSQL ka internal storage engine row ko microsecond level pe serialize karta hai. Nateeja: Zero deadlocks, zero lock convoys, aur 500 concurrent requests 100 milliseconds ke andar process ho kar khatam ho jati hain!
10. TRANSACTIONAL OUTBOX PATTERN KYUN LAZMI HAI? Reliability Engineering
DUAL-WRITE PROBLEM Direct Message Publishing Ka Khatra
Agar hum database mein booking save karein aur agle line pe RabbitMQ/Kafka ya payment service ko HTTP call karein: Agar booking save ho gayi lekin server crash ho gaya ya network toot gaya, to message kabhi publish nahi hoga! User ke paise kat jayenge lekin ticket generate nahi hogi.
OUTBOX PATTERN SOLUTION Guaranteed At-Least-Once Delivery
Hum booking record aur outbox event ko aik hi database ACID transaction ke andar likhte hain. Dono sath commit hote hain ya dono sath rollback hote hain. Background saga poller in events ko read karta hai. Agar server 10 baar bhi crash ho, restart hone par koi event miss nahi hota!
Why Redis Only for Caching and NOT for Inventory Counts? Redis bohot fast hai, lekin Redis asynchronous disk persistence (RDB/AOF) par chalta hai. Agar server band ho jaye to aakhri 1 second ka data loss ho sakta hai. Airline inventory mein 1 second ka data loss hone ka matlab hai hazaaron seats ka ghapla! Is liye single source of truth PostgreSQL Citus hai, jabke Redis sirf speed boost cache hai.

12. CITUS TABLE CO-LOCATION (THE SECRET TO ZERO-NETWORK-OVERHEAD 2PC) Crucial Concept
WHAT IS CO-LOCATION? Aasan Roman Urdu Mein Samajhein
Distributed databases mein sab se bara masla yeh hota hai ke agar flights table aik computer par ho aur flight_seats table doosre computer par ho, to booking ke waqt dono computers ko network par baat karni parti hai (Distributed Two-Phase Commit - 2PC), jis se speed 90% gir jati hai.
Hum ne Citus mein command chalayi:
SELECT create_distributed_table('flight_seats', 'flight_id', colocate_with => 'flights');
Iska Faida: Citus ensure karta hai ke jis worker node par flight_id = 4500 ki flight store hai, usi worker node ki usi physical disk par uski seats bhi store hongi! Booking ke waqt koi cross-network talk nahi hoti, query local machine pe microsecond mein execute hoti hai!

17. TOP EXAMINER QUESTIONS: SHARDING, CONCURRENCY & CAP THEOREM Viva Preparation
Q1 Citus mein Shard Key ke tor par 'flight_id' kyun chuni gayi, 'user_id' ya 'date' kyun nahi?
Answer: Shard key chunne ka golden rule yeh hai ke "Transactions hamesha aik hi shard par execute honi chahiyein." Airline inventory mein booking seat inventory flight ke hisab se hoti hai, user ke hisab se nahi. Agar hum user_id chunte to flight inventory alag worker pe hoti aur user alag worker pe, jis se cross-worker distributed locking karni parti. flight_id chunne se aik flight ki tamam seats aik hi worker par rehti hain, aur booking ultra-fast local transaction ban jati hai.
Q2 CAP Theorem mein AeroScale kahan stand karta hai? CP ya AP?
Answer: Hum ne system ko business requirement ke mutabiq split kiya hai:
1. Seat Hold & Booking Engine = CP (Consistency & Partition Tolerance): Agar network partition ya split aye to hum booking reject (fail) kar denge, lekin kisi surat mein inconsistent data ya double-booking accept nahi karenge.
2. Flight Search Engine = AP (Availability & Partition Tolerance): Search ke liye CQRS read replica use hota hai jo hamesha available rehta hai. Agar 50ms ka eventual consistency replication lag ho bhi to user ko koi farq nahi parta.
Q3 Citus Table Co-Location na karne se kya nuksan hota?
Answer: Agar co-location na hoti to flights table shard 101 Worker1 par hota aur flight_seats shard 101 Worker2 par hota. Har booking ke liye Coordinator ko Two-Phase Commit (2PC) chalana parta: Worker1 se prepare mango, Worker2 se prepare mango, phir dono ko commit bolo. Is se network latency barhti hai, locks hold rehte hain, aur throughput 2500 req/sec se gir kar sirf 80 req/sec reh jati!
Q4 Race condition kya hoti hai aur AeroScale ne isay software mein solve kiya ya DB mein?
Answer: Race condition tab hoti hai jab do threads aik hi resource (last seat) ko sath read karte hain aur dono samajhte hain ke resource available hai. AeroScale ne isay application code (Node.js) mein solve karne ke bajaye PostgreSQL storage engine level par solve kiya. Atomic conditional query UPDATE ... WHERE available_seats >= 1 chala kar database engine ke internal row-lock ko use kiya, jahan koi do threads aik waqt mein row modify nahi kar sakte.
Q5 Citus worker nodes ke darmiyan maintenance daemon auth error kya tha aur kaise theek kiya?
Answer: Citus workers ko cluster maintenance, shard statistics sync aur rebalancing ke liye aik doosre se direct connect hona parta hai. Worker2 worker1 ko call karte waqt fe_sendauth: no password supplied throw kar raha tha kyunke internal Docker network pe trust authentication configuration missing thi. Hum ne internal docker network mein pg_hba.conf trust rules configure kiye jis se worker-to-worker internal communication authenticate ho gayi aur cluster 100% healthy ho gaya.
Q6 Agar Citus Coordinator crash ho jaye to kya system band ho jayega?
Answer: Production environment mein Citus Coordinator ka Hot Standby Replica hota hai jo Patroni / Raft consensus ke sath configure hota hai. Agar primary coordinator fail ho to automatic failover hota hai aur virtual IP standby coordinator par shift ho jati hai. Workers ka data intact rehta hai kyunke data shards workers ki apni physical disks par safe hote hain.

18. DATABASE INTERNALS, DEADLOCKS & SAGA ARCHITECTURE Viva Deep-Dive
Q7 Transaction Isolation Level kaunsa use ho raha hai aur SERIALIZABLE kyun nahi lagaya?
Answer: Hum Read Committed with Atomic Conditional Decrement use kar rahe hain. Bohot se log sochte hain ke zero-oversell ke liye SERIALIZABLE isolation zaroori hai. Asal mein SERIALIZABLE isolation heavy concurrency mein Serialization Failure (SQLSTATE 40001) throw karta hai, jis se 80% genuine users ki transactions abort ho jati hain aur complex retry loops lagane parte hain. Hamari conditional atomic update query Read Committed par bhi 100% mathematical zero-oversell guarantee deti hai bina kisi abort penalty ke.
Q8 Distributed Deadlocks se bachne ke liye AeroScale mein kya mechanism hai?
Answer: Deadlock tab hota hai jab Transaction A ne Seat 1 lock ki aur Seat 2 ka wait kar rahi hai, jabke Transaction B ne Seat 2 lock ki aur Seat 1 ka wait kar rahi hai. AeroScale mein do safety measures hain:
1. Deterministic Lock Sorting: Multiple seats book karte waqt application hamesha seat IDs ko ascending numerical order mein sort karke lock karti hai. Circular wait ka imkaan khatam ho jata hai.
2. Single-Worker Co-location: Query single worker pe rehti hai jahan Postgres ka local deadlock detector (deadlock_timeout) kisi cycle ko foran detect karke abort kar deta hai.
Q9 60 Million records par search pagination itni fast (< 40ms) kaise kaam karti hai?
Answer: Agar hum naive SELECT * FROM flights LIMIT 10 OFFSET 5000000 chalate to Postgres ko 5 Million rows sequentially disk se scan karni partin, query 15 second mein timeout hoti. Hum ne CQRS Read Replica par Composite B-Tree Covering Indexes banaye hain (origin, destination, departure_date, flight_id) par. Database index seek karta hai aur memory pointer se agle 10 rows foran utha leta hai bina table scan kiye.
Q10 Saga Orchestration aur Saga Choreography mein kya farq hai aur hum ne Orchestration kyun chuni?
Answer: Choreography mein microservices aik doosre ke events listen karke faisla karti hain (decentralized). Airline systems mein yeh dangerous hai kyunke agar 5 services hon to kisi ko poori state ka pata nahi hota aur debugging mushkil ho jati hai. Orchestration mein aik Central Coordinator (hamara backend Saga service) hota hai jisko exact pata hota hai ke seat hold hui ya nahi, payment aayi ya nahi, aur 300 second baad kisko rollback karna hai. Clear visibility aur easy audit trail milti hai.
Q11 Agar CQRS Read Replica crash ho jaye to kya bookings ruk jayengi?
Answer: Bilkul nahi! Yahi to CQRS ka sab se bara faida hai. Read Replica sirf search queries serve karta hai. Agar Read Replica temporarily crash bhi ho jaye to booking transactions jo Citus Coordinator (Port 55432) par ja rahi hain woh 100% chalti rehti hain. Search traffic fallback cache se serve ho sakti hai.
